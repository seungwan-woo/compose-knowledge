> **용어:** 아래 코드의 Runtime `computedStateOf`는 공식 API 레퍼런스에 **Added in 1.13.0-rc01**로 표기된 새로운 API입니다. Stable 1.12 기반 프로젝트에 그대로 붙여넣으면 사용할 수 없습니다. 프리릴리스 환경의 Kotlin·AGP·compileSdk 요구도 함께 점검하세요.

## 1. `computedStateOf` vs `derivedStateOf`

공통점은 파생 State의 **결과값 변화**를 관찰한다는 점입니다. 차이점은 `computedStateOf`는 **읽을 때마다 계산**하며 결과를 캐시하지 않는 반면, `derivedStateOf`는 계산 결과를 캐시한다는 점입니다.

### 저비용 계산: `computedStateOf` (1.13.0 RC+)

~~~kotlin
import androidx.compose.foundation.lazy.rememberLazyListState
import androidx.compose.material3.Text
import androidx.compose.runtime.Composable
import androidx.compose.runtime.computedStateOf
import androidx.compose.runtime.getValue
import androidx.compose.runtime.remember

@Composable
fun ComputedScrollStatus() {
    val listState = rememberLazyListState()
    val showButton by remember(listState) {
        computedStateOf { listState.firstVisibleItemIndex > 0 }
    }
    Text(if (showButton) "위로 이동" else "첫 항목")
}
~~~

이전 세션 코드에서 단순하게 적었던 `remember { computedStateOf { ... } }`와 의미는 같고, 여기서는 listState를 명시적인 key로 둡니다. 입력 상태 변경 때 출력이 동일한 경우 이를 구독한 Composition의 불필요한 갱신을 줄일 수 있지만 계산 비용은 매번 발생할 수 있습니다. 계산 블록 안에서는 상태 쓰기(side effect)를 하지 마세요.

### 비용이 큰 계산: `derivedStateOf` (1.0.0+)

~~~kotlin
import androidx.compose.runtime.Composable
import androidx.compose.runtime.State
import androidx.compose.runtime.derivedStateOf
import androidx.compose.runtime.remember

@Composable
fun rememberFilteredCount(numbers: State<List<Int>>): State<Int> =
    remember(numbers) {
        derivedStateOf { numbers.value.count { it > 100 } }
    }
~~~

위 계산은 목록 크기에 비례하여 비용이 커질 수 있어 결과 캐싱이 유용할 수 있습니다. 실제 병목인지 측정하고, 과도한 파생 상태 객체가 생기지 않도록 관리해야 합니다.

**버전·AGP:** `computedStateOf` = **Runtime 1.13.0-rc01+ (RC)**; `derivedStateOf` = **Runtime 1.0.0+**. `computedStateOf`를 쓰는 Compose 1.13 프로젝트는 **AGP 9.0+ / compileSdk 37** 기준 및 해당 1.13 릴리스의 Kotlin 요구사항을 점검해야 합니다. 구형 API 자체에 별도 AGP 하한은 없습니다. **검증:** 정확한 API 계약 확인, 앱 빌드 미실행.

**공식 근거:** [Runtime package summary](https://developer.android.com/reference/kotlin/androidx/compose/runtime/package-summary) · [Compose 성능 가이드](https://developer.android.com/develop/ui/compose/performance)

## 2. `graphicsLayer`: Animation State를 Draw 단계에서 읽기

**Before:** 애니메이션 값을 Composition에서 읽으면 매 프레임 해당 상태를 구독하는 Composition이 다시 실행될 수 있습니다.

~~~kotlin
import androidx.compose.animation.core.animateFloatAsState
import androidx.compose.foundation.layout.Box
import androidx.compose.foundation.layout.size
import androidx.compose.runtime.Composable
import androidx.compose.runtime.getValue
import androidx.compose.ui.Modifier
import androidx.compose.ui.draw.alpha
import androidx.compose.ui.unit.dp

@Composable
fun FadeBefore(targetAlpha: Float) {
    val alpha by animateFloatAsState(
        targetValue = targetAlpha,
        label = "alpha"
    )
    Box(Modifier.size(48.dp).alpha(alpha))
}
~~~

**After:** `State.value` 읽기를 `graphicsLayer` 블록 내부로 이동합니다.

~~~kotlin
import androidx.compose.animation.core.animateFloatAsState
import androidx.compose.foundation.layout.Box
import androidx.compose.foundation.layout.size
import androidx.compose.runtime.Composable
import androidx.compose.ui.Modifier
import androidx.compose.ui.graphics.graphicsLayer
import androidx.compose.ui.unit.dp

@Composable
fun FadeAfter(targetAlpha: Float) {
    val animatedAlpha = animateFloatAsState(
        targetValue = targetAlpha,
        label = "alpha"
    )
    Box(
        Modifier.size(48.dp).graphicsLayer {
            alpha = animatedAlpha.value
        }
    )
}
~~~

**관찰:** 이 State 읽기는 Draw 단계에서 수행되므로, 해당 값에 의해 Composition/Layout을 다시 실행할 필요가 없습니다. 단 **GPU 레이어와 합성 비용**, 다른 곳의 State 읽기는 별도 검증해야 합니다.

### Layout(배치) 단계로 State 읽기 지연: `offset { }`

~~~kotlin
import androidx.compose.foundation.layout.Box
import androidx.compose.foundation.layout.size
import androidx.compose.runtime.Composable
import androidx.compose.runtime.State
import androidx.compose.ui.Modifier
import androidx.compose.foundation.layout.offset
import androidx.compose.ui.unit.IntOffset
import androidx.compose.ui.unit.dp

@Composable
fun MovingBox(offsetPx: State<Int>) {
    Box(
        Modifier.size(48.dp)
            .offset { IntOffset(0, offsetPx.value) }
    )
}
~~~

이 람다는 **픽셀** 단위 `IntOffset`을 반환합니다. 위치 변화가 배치 단계에만 영향을 주는 경우 Composition 단계의 상태 읽기보다 효율적일 수 있습니다.

**버전·AGP:** `Modifier.graphicsLayer`, `Modifier.offset { }`, `Modifier.alpha` 및 `animateFloatAsState`의 사용 예시는 Compose UI/Animation **1.0.0+ 계열 API**를 기준으로 합니다(세부 overload는 사용 버전의 API 확인). **API 자체의 AGP 하한은 없고**, Compose 1.12.0+를 채택한 경우 **AGP 9.0+ / compileSdk 37**이 필요합니다. **측정 결과는 아님**.

**공식 근거:** [Modifier phases](https://developer.android.com/develop/ui/compose/performance/modifier-phases) · [Compose practical performance codelab](https://developer.android.com/codelabs/jetpack-compose-performance)

## 3. `LaunchedEffect` key와 `rememberUpdatedState`

화면이 살아 있는 동안 기다리는 타이머에서 콜백 함수 객체만 바뀌었다고 타이머를 재시작할 필요는 없을 수 있습니다.

~~~kotlin
import androidx.compose.runtime.Composable
import androidx.compose.runtime.LaunchedEffect
import androidx.compose.runtime.getValue
import androidx.compose.runtime.rememberUpdatedState
import kotlinx.coroutines.delay

@Composable
fun TimeoutEffect(
    timeoutMs: Long,
    onTimeout: () -> Unit
) {
    val latestOnTimeout by rememberUpdatedState(onTimeout)

    // timeoutMs가 바뀔 때만 타이머 재시작
    LaunchedEffect(timeoutMs) {
        delay(timeoutMs)
        latestOnTimeout()
    }
}
~~~

`rememberUpdatedState(onTimeout)`는 **현재 콜백을 읽되 Effect는 재시작하지 않게** 합니다. 다만 `timeoutMs`는 key이므로 바뀌면 이전 코루틴이 취소되고 새 지연이 시작됩니다. 초기 Composition에서도 Effect는 실행됩니다.

**리뷰:** 키에 빠진 입력은 없는지, 콜백 변경이 타이머 재시작을 요구하는지, Composable이 사라졌을 때 자동 취소되는 것이 맞는지 확인합니다.

**버전·AGP:** `LaunchedEffect`, `rememberUpdatedState` = Compose Runtime 1.0.0+ 계열. **기능 자체의 별도 AGP 최소 버전 없음**; 채택하는 Compose 의존성의 toolchain 요구에 종속. **검증:** 공식 샘플 의미와 대조, 실행 테스트 미실행.

**공식 근거:** [Side-effects in Compose](https://developer.android.com/develop/ui/compose/side-effects) · [Runtime API](https://developer.android.com/reference/kotlin/androidx/compose/runtime/package-summary)
