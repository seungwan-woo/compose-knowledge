## 1. Fix stale values after switching between light and dark

**Symptom.** Switching the system theme recomposes the composable, but the color held by <code>remember { mutableStateOf(...) }</code> stays the same.

### Problem example that remembers the initial theme value

~~~kotlin
import androidx.compose.foundation.isSystemInDarkTheme
import androidx.compose.material3.Text
import androidx.compose.runtime.Composable
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.remember
import androidx.compose.ui.graphics.Color

@Composable
fun StaleThemeLabel() {
    val dark = isSystemInDarkTheme()
    val textColor by remember {
        mutableStateOf(if (dark) Color.White else Color.Black)
    }
    Text("Status", color = textColor)
}
~~~

The <code>remember</code> initializer runs again in the same composition only when its key changes. **Recomposition and state initialization are separate operations.**

### Improved example that derives the value from the theme

~~~kotlin
import androidx.compose.foundation.isSystemInDarkTheme
import androidx.compose.material3.Text
import androidx.compose.runtime.Composable
import androidx.compose.ui.graphics.Color

@Composable
fun ReactiveThemeLabel() {
    val dark = isSystemInDarkTheme()
    val textColor = if (dark) Color.White else Color.Black
    Text("Status", color = textColor)
}
~~~

For apps with a custom design system or Material 3, child components can usually read tokens such as <code>MaterialTheme.colorScheme.onSurface</code> directly. **The app's theme selection can differ from the system theme.**

**Code review.** Look for theme resources copied or cached in <code>remember</code>, a View context, a singleton, or a separate <code>mutableStateOf</code>. Using <code>remember(dark)</code> reinitializes the value, which can also reset user edits.

**Versions.** <code>isSystemInDarkTheme</code> (Foundation 1.0.0+) and <code>remember</code> (Runtime 1.0.0+). The Material 3 example requires the app's Material 3 dependency.

**Sources.** [isSystemInDarkTheme API](https://developer.android.com/reference/kotlin/androidx/compose/foundation/isSystemInDarkTheme.composable) · [remember API](https://developer.android.com/reference/kotlin/androidx/compose/runtime/remember.composable) · [State in Compose](https://developer.android.com/develop/ui/compose/state)

## 2. Read scroll state in the draw phase

**Symptom.** Scrolling changes only a shadow or overlay. Reading the frequently changing scroll state during composition triggers unnecessary recomposition.

~~~kotlin
import androidx.compose.foundation.ScrollState
import androidx.compose.foundation.layout.Box
import androidx.compose.foundation.layout.fillMaxWidth
import androidx.compose.foundation.layout.height
import androidx.compose.ui.Modifier
import androidx.compose.ui.draw.drawBehind
import androidx.compose.ui.graphics.Color
import androidx.compose.ui.unit.dp
import androidx.compose.runtime.Composable

@Composable
fun ScrollEdgeShade(scrollState: ScrollState) {
    Box(
        modifier = Modifier
            .fillMaxWidth()
            .height(10.dp)
            .drawBehind {
                // State를 Composition이 아닌 Draw 단계에서 읽는다.
                val overlayAlpha =
                    if (scrollState.value > 0) 0.35f else 0f
                drawRect(Color.Black, alpha = overlayAlpha)
            }
    )
}
~~~

A change to state read inside <code>drawBehind</code> can invalidate that draw work. **This state read alone leaves composition and layout unaffected.** Other composition code that reads the same state can still recompose independently.

**How to check.** (1) Check recomposition counts in Android Studio Layout Inspector. (2) Move the state read into the draw lambda. (3) Measure the change in frame performance with a tool such as Macrobenchmark or Perfetto. Drawing still has a cost, so measure the result.

**Versions.** <code>Modifier.drawBehind</code> is available in Compose UI 1.0.0+. The example uses Compose UI 1.7.8.

**Sources.** [drawBehind API](https://developer.android.com/reference/kotlin/androidx/compose/ui/draw/drawBehind.modifier) · [Compose phases and state reads](https://developer.android.com/develop/ui/compose/phases) · [Modifier phases](https://developer.android.com/develop/ui/compose/performance/modifier-phases)

## 3. Verify theme changes with screenshot pixel tests

**Goal.** Verify that light and dark modes render differently on a simple screen. The example is a **pixel smoke test**. Full golden regression testing requires separate reference images and comparison tools.

~~~kotlin
import androidx.compose.foundation.background
import androidx.compose.foundation.layout.Box
import androidx.compose.foundation.layout.size
import androidx.compose.runtime.mutableStateOf
import androidx.compose.ui.Modifier
import androidx.compose.ui.graphics.Color
import androidx.compose.ui.graphics.toPixelMap
import androidx.compose.ui.platform.testTag
import androidx.compose.ui.test.captureToImage
import androidx.compose.ui.test.junit4.createComposeRule
import androidx.compose.ui.test.onNodeWithTag
import androidx.compose.ui.unit.dp
import org.junit.Assert.assertEquals
import org.junit.Rule
import org.junit.Test

class ThemePixelTest {
    @get:Rule val rule = createComposeRule()

    @Test fun themeStateUpdatesPixel() {
        val dark = mutableStateOf(false)
        rule.setContent {
            Box(
                Modifier
                    .size(48.dp)
                    .background(if (dark.value) Color.Black else Color.White)
                    .testTag("theme-surface")
            )
        }

        val light = rule.onNodeWithTag("theme-surface")
            .captureToImage().toPixelMap()[24, 24]
        assertEquals(Color.White, light)

        rule.runOnIdle { dark.value = true }

        val darkPixel = rule.onNodeWithTag("theme-surface")
            .captureToImage().toPixelMap()[24, 24]
        assertEquals(Color.Black, darkPixel)
    }
}
~~~

**Requirements.** Android instrumentation tests (<code>androidTest</code>), JUnit 4, UI Test dependencies such as <code>androidx.compose.ui:ui-test-junit4</code>, and **API level 26 or later on the capture device**. The test changes **test state**. To test actual system theme or configuration transitions, control those settings separately.

**Regression matrix.** Light/dark × fontScale 1.0/1.3 × LTR/RTL × screen size. UI fonts and brushes can produce pixel differences, so check for defects in **specific areas such as borders, text, and colors** as well as overall image similarity.

**Tool selection.** Consider the available testing approaches when choosing which one to adopt. The existing `ui-test-junit4` approach requires a target app and device. AGP 9.5 or later also offers experimental Preview-based Test Suites integration. The official docs mark the standalone `com.android.compose.screenshot` plugin path as deprecated.

## 4. Preserve item state with stable keys in lazy lists (additional review tip)

If a list is frequently sorted or has items inserted and removed, use each **item's unique ID** as its key. Without a key, moving items can unexpectedly associate `remember` state and effects with different items. Each key must be unique within the list.

~~~kotlin
import androidx.compose.foundation.lazy.LazyColumn
import androidx.compose.foundation.lazy.items
import androidx.compose.material3.Text
import androidx.compose.runtime.Composable

data class ReviewRow(val id: Long, val label: String)

@Composable
fun ReviewList(rows: List<ReviewRow>) {
    LazyColumn {
        items(
            items = rows,
            key = { row -> row.id }
        ) { row ->
            Text(text = row.label)
        }
    }
}
~~~

**Reproduce.** Insert an item with a stable ID in the middle of the list and check whether existing items retain their state and scroll position. `key = { index }` changes as items are reordered. If item state must be restored on Android, check that the key type can be stored in a Bundle.

**Code review.** [ ] Unique IDs [ ] Per-item state before and after reordering [ ] Scroll behavior on removal and insertion [ ] `rememberSaveable` restoration [ ] Effect restarts as the list changes.

**Versions and tools.** Foundation `LazyColumn` and `items(key)` are available from 1.0.0. The example uses Compose Foundation 1.7.8. Kotlin, JDK, and compileSdk depend on the selected Compose and AGP versions. The APIs have no separate AGP minimum. **Compilation and device tests unrun.**

**Official sources.** [Lazy lists](https://developer.android.com/develop/ui/compose/lists#item-keys) · [LazyListScope API](https://developer.android.com/reference/kotlin/androidx/compose/foundation/lazy/LazyListScope)

## Review checklist

- [ ] Do theme-derived values avoid unnecessary caching via <code>remember { mutableStateOf(...) }</code>?
- [ ] Are scroll and animation state read in the phase that needs them?
- [ ] Are the system theme and the app's own theme treated as separate sources of truth?
- [ ] Do tests check the rendered pixels as well as the screen state?
- [ ] Have you verified the Compose and UI Test versions, **minimum supported AGP**, compileSdk, and Kotlin together?

**Verification.** The examples are based on official APIs and guides. This repository has no Android app module, so Android builds and device tests were unrun. Verify the versions and devices used by your project before adopting the examples in production.
