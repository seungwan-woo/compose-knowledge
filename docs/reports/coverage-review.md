## Resolved finding

**Resolved P2 — Foreign imports became exact local API aliases.** `src/refresh/crawl.ts:72–75` attaches a configured API FQN whenever the section contains its short name, including an import of a different package's same-named function. This introduces incorrect package attribution into the new exact-symbol search path (`src/retrieval/search.ts:10–17`). In the generated corpus, querying `androidx.compose.ui.unit.lerp` returns `live-androidx-ui-ui-unit-ui-unit-dp-lines-1` first, although that section's only `lerp` occurrence is `import androidx.compose.ui.util.lerp`. Querying `androidx.compose.ui.unit.min` additionally returns `live-androidx-ui-ui-unit-ui-unit-dp-lines-36` because it contains `import kotlin.math.min`; it contains no reference to the configured Compose `min` API. These are concrete false exact matches, not merely broad textual search results. Ignore import/package directives when deciding section aliases (or resolve their actual identity), preserve those directives in the original source body, and add regressions for these collisions. This is relevant to the specification's requirement for correct package/API identity and actual upstream provenance.

Scoped re-review confirmed the fix at `src/refresh/crawl.ts:72`: non-HTML alias scanning excludes package/import directive lines while keeping the original source body and provenance untouched. The added regression checks an import-only chunk and a separate declaration chunk. An independent local replay with the actual cached `Dp.kt` confirmed that both false aliases are absent, both original imports remain in the body, and genuine `ui.unit.lerp`/`ui.unit.min` declaration aliases remain discoverable. No network requests or compiler runs were needed.
